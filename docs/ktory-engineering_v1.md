# Ktory 工程设计：原规格审查与修订路线

日期：2026-09-24  
状态：工程讨论稿 v0.1；尚非可直接实施的冻结规格

## 1. 文档职责与依据

本文件处理语言、解析、执行、数据结构、接入和验证问题，并随工程讨论更新。

- `ktory-scope.md`：决定做什么、阶段目标和责任边界，是需求依据。本轮依据其已确认首阶段验收及多语言回退决策。
- 原版 `ktory.md`：初始工程方案；下文按原文节号定位审查项。
- 本文件：解释原方案如何保留、修订或延期，记录候选方案和待决问题。

本次不改写原版，也不向 scope 填入新的工程规则。工程方案如需要改变 scope，应先明确提出需求变更，不能通过接口设计暗中扩大范围。

### 状态标记

- **需求已确认**：来自 scope，可作为工程约束。
- **必须修订**：原方案与需求冲突，或不足以表达原方案自身的行为；修订方向仍可讨论。
- **建议保留／候选方案**：工程建议，不代表用户已确认具体实现。
- **已推迟**：scope 明确不要求第一阶段交付。
- **待决**：需要作出工程决定，不能由本文示例自动定案。

实现语言、核心是否共用同一二进制或源码、VS Code 与 Web 的最终选型均未确定。下文的字段及接口名仅用于说明契约，不是冻结 API。

## 2. 首阶段工程约束

这里只引用工程所需的 scope 结论，不重新定义产品范围。

| 约束 | 对工程设计的影响 |
| --- | --- |
| 日系视觉小说是主要创作参照；脚本组织调查也需充分支持 | 先验证线性对白、选择与汇流，再补全循环调查；不删去后者，也不以复杂循环状态主导架构 |
| 脚本无显式异步演出等待；游戏决定何时发送 next | 核心不能把外部演出完成作为隐式推进前提 |
| 文本播放完成开启文本门控 | 保留文本就绪概念；具体由播放器还是接入层检查，仍需定案 |
| 演出推进限制在游戏侧配置 | 不添加脚本级等待演出或演出阻塞策略语法 |
| Unity 首阶段只需对话框、立绘显示 | Timeline 集成不是首阶段接口和验收的前置条件 |
| 独立试读、语言选择为首阶段必需 | Unity 之外也必须可解析和执行基础剧情 |
| 试读跳过非基础行为，未知外部选项条件忽略并展示选项 | 试读执行策略应与真实游戏区分，不能把宽松行为带入正式运行 |
| 同文件多语言，缺译回退文件默认语言；输出实际语言 | AST 及输出载荷都需要语言信息 |
| 首阶段不要求存档，最终需要逐句恢复 | 运行时仍有执行位置和会话状态；暂不实现持久化、回滚或完整快照 |

## 4. 优先解决的契约问题

### E01：next、文本就绪和演出限制的边界

**优先级：P0，影响核心执行模型。** 依据原文 §2.3、§5.2–5.3 和 scope D10–D15。

原文阶段二允许等待 Handler 完成，`.next` 又要求前置演出完成；这与不等待外部演出的要求冲突。原文还把选择、文本和其他业务共用一个 `canAdvance`，容易把宿主的限制变成核心状态。

建议拆分以下概念：

| 概念 | 职责边界 |
| --- | --- |
| 玩家原始点击 | 游戏或试读器输入；不等于核心必然接收到 next |
| 文本快显请求 | 作用于当前句的呈现；受 `.skippable(false, 3)` 等文本策略限制 |
| 文本就绪 | 当前句完成播放，满足文本推进条件；如何通知及在哪里校验待决 |
| next | 请求从当前可推进位置继续；核心不查询角色是否到达等演出状态 |
| 选择提交 | 指定某一选项，不能由普通 next 猜测选择 |
| 演出限制 | 游戏侧决定保留、忽略点击或允许跳过，并决定何时发送 next |

**候选模型**：核心在一次输入后同步执行到下一个文本、选择或文件结束位置，输出结果后返回；外部异步播放独立进行。这里的“同步”不意味着一个调用播放完整个场景，也不意味着核心没有当前位置。

文本就绪有两种仍需选择的承载方式：核心接收文本就绪通知后允许 next；或宿主承担文本门控，仅向核心发送有效 next。两者都不能扩展为核心等待演出。此处不能凭“脚本不异步”直接替用户决定。

重复／过期输入需要关联当前呈现位置，避免上一句的延迟通知推进下一句。建议使用会话内呈现标识；它不同于未来存档使用的稳定内容标识。

`.next(waitTime)` 的计时归属、快显后是否立即计时、与玩家输入竞争如何处理，均为待决。候选方向是计时方发送同类推进请求，避免第二条绕过校验的推进路径。首阶段不要求实现未来的演出限制系统，但不能继续沿用“核心先等演出”的定义。

### E02：语法必须能够唯一生成结构

**优先级：P0，影响解析及编辑诊断。** 依据原文 §2.1–2.4。

| 原文问题 | 需要明确的规则 |
| --- | --- |
| `#do` 的名称被说成仅供阅读，`#choice` 的名称却选择处理器 | 名称的结构作用与运行时分发作用分别定义；不要同时宣称所有名称都无语义 |
| `#name` 同时满足指令和容器语法 | 选择结构性区分方式，例如子项结构或显式声明；具体方案待决，不让 Parser 查询 Unity 注册表决定 AST 类型 |
| 修饰符“最近锚点吸附、与缩进无关”，内联分支却依赖缩进 | 定义能否跨出分支附着，容器结束后的修饰符归属；不得靠实现者猜测 |
| 对白内容允许普通文本，行尾也允许修饰符 | 正文中的 `.name(...)` 何时是文字？引号、转义、扫描范围需完整定义 |
| 旁白按保留前缀排除，但 `//` 注释只出现在样例中 | 正式规定注释及空行处理，避免将注释解析成旁白 |
| `? {expr}` 守卫只在字段说明及样例中局部出现 | 补全可用位置、作用域、与选项／锚点的组合顺序 |
| 行内条件只有分段开头，未定义终止和嵌套 | 明确条件作用到行末还是有结束符，是否允许多个条件段 |

工程上建议先固定结构语法，再扩展富文本与表达式。暂不改变作者熟悉的语法外观，但也不为保留外观留下不可消解的歧义。

### E03：AST 与控制流规范不一致

**优先级：P0。** 依据原文 §3–4。

原文 `StepNode` 只有 Text、Directive、Container，但 §3 和 §6 出现独立的 `-> return`、`-> break`、普通跳转等。当前 AST 没有承载这些语句的位置。

建议增加明确的控制流节点，或给出另一种无损表示；不能只支持选项上的 `targetJump`。此外：

- `targetJump` 与 `inlineSteps` 都可选，类型允许两者同时存在，需规定互斥或执行次序。
- `-> Label`“放弃当前执行上下文”没有说明清除哪些调用帧及容器帧。
- `-> end` 的“节”没有正式结构定义；块末尾、文件末尾也缺少规则。
- §3.1 称三类拓扑互斥，但 §6 混合循环容器与内联分支。普通内联分支结束后汇流，与循环内联分支是否重开菜单必须分别定义。
- 一次性选项的访问标记何时写入、生命周期到哪里结束，尚未定义。隐藏／置灰属于显示策略，不能让独立试读与 Unity 各自决定是否还能选。

**最小验证样例**：普通选择汇流、调用返回、循环选择中内联返回菜单、一次性项消耗、退出循环、无有效选项、块末尾不意外跌入子过程。

### E04：多语言不是单个 TextStep 的附加字典

**优先级：P0。** 依据原文 §2.2.1、§4–5.2，以及 scope 的语言决策。

已经确定：同文件语言变体；试读器可选语言；缺译回退默认语言；输出标记实际语言。

必须补的结构：

| 对象 | 原版缺口 | 候选补充 |
| --- | --- | --- |
| 文件 | 只有 blocks | 文件元信息及 `defaultLang` |
| 输出载荷 | 无语言标识 | `content` 与实际 `language`；请求语言保留在会话配置中 |
| 选项 | `label: string` 单语言 | 选项标签也使用可本地化文本；需补作者语法 |
| 说话人 | 名称直接作为 speaker | 区分稳定角色引用与显示名是否有必要，待决；不能擅自要求完整角色数据库 |

候选解析流程：选定请求语言 → 找不到该译文则查文件默认语言 → 按所选文本输出实际语言。请求英文回退中文时输出 `zh`，不改写会话的请求语言，因此下一句仍优先查英文。

`defaultLang` 的声明语法、是否必填、未标注正文如何归属、默认译文也缺失时如何处理，仍未定。空字符串是否算缺译也需明确。一个菜单中各选项可能回退到不同语言，建议语言标识随每项文本携带，不用一个菜单级语言覆盖全部选项。

切换语言是否立即刷新当前句尚未确认。若允许，候选约束是只重新解析展示文本，不重跑本句获得钥匙或立绘触发等副作用；否则语言切换可能重复修改剧情状态。

### E05：内部叙事状态与外部求值应可区分

**优先级：P0 定边界，P1 实现基础能力。** 依据原文 §4–5.2。

原版把条件与插值交给 Lua/C# 门面，但当前需求要求纯叙事记录无需下放宿主，且独立试读应能执行基础行为。

候选分工：核心或随核心提供的基础模块维护会话内访问／选择记录；外部求值接口提供背包等游戏状态。基础记录集与表达式子集尚需确认，不能为低频循环调查直接引入完整脚本语言。

外部结果不能只有布尔值：试读器需要区分“已知为假”和“此环境无法求值”。建议结果区分已知值、缺少能力及错误；无效语法不应伪装成缺少宿主能力。

获得钥匙等操作默认在脚本中声明，并不意味着背包数据由核心持有。操作可以交给宿主执行；允许外部独立实现不等于两边同时执行同一操作。

### E06：独立试读的宽松边界

**优先级：P1；基础行为清单需在实现前明确。**

| 情况 | 首阶段规则或待决项 |
| --- | --- |
| 支持的基础对白、选择和控制流 | 正常执行；具体基础语法清单需与 E02–E05 对齐 |
| 不支持的演出修饰符 | 跳过该行为，保留其所属对白 |
| 无法求值的外部选项条件 | 忽略条件，展示全部相关选项；仍由作者选择，不自动执行全部分支 |
| 可以求值的基础条件 | 不因“展示全部未知选项”而自动忽略 |
| 未知外部插值 | 采用原表达式还是占位文本待决，不伪造游戏数据 |
| 未知行内条件分支 | 与选项菜单不同，不能自动套用“把所有分支一起执行”；展示规则待决 |
| 不支持的自定义容器 | 如何跳过整个结构或使用基础表示待决；不能任意顺序执行其中全部子项 |
| 文件本身语法错误 | 建议报告源位置；跳过外部能力不等于吞掉无法解析的结构 |

上述未决项是小型展示规则，不用于引入外部状态模拟器。试读器不负责复现游戏侧推进限制，也不验证真实演出。

### E07：跨环境文本与核心复用

**优先级：P1，核心选型前明确策略。**

原版将 Markdown 在解析阶段直接转成目标引擎标签，同时要求引擎无关。这样会让试读端被迫解释引擎文本，或引入两套不一致的脱糖规则。

候选方向：结构解析保留原文及语言变体；共享文本规则产生中立样式片段，或在各表现适配器转换。具体中间表示及首阶段富文本集合待决。原文举出的目标引擎注音标签仅是初稿示意，本审查不确认其实际支持；选择具体渲染器时再验证。

Web/VS Code 与 Unity 如何共用核心需要专项选择。可比较共享核心、可移植编译产物或多个实现共用规范等路径；目前不直接指定 TypeScript 或 C#。若最终出现多个执行实现，必须使用同一组语义样例验证，而不只比较画面。

## 5. 候选模块划分与数据形状

以下为工程建议，待 E01–E05 定案后再编写正式接口。

| 模块 | 负责 | 不承担 |
| --- | --- | --- |
| Parser／结构校验 | 源码到结构、源位置、静态错误 | 场景状态、资源播放 |
| 剧情播放器 | 执行位置、控制流、基础叙事记录、输出下一内容 | 等待角色移动或检查演出结束 |
| 语言解析 | 请求语言选择、默认语言回退、实际语言标识 | 翻译管理、配音 |
| 扩展分发／求值接口 | 传递宿主指令，区分可求值与不可求值 | 把所有扩展都变成必需异步任务 |
| 试读接入 | 语言选择、基础展示、宽松外部能力处理 | 模拟完整游戏 |
| Unity 接入 | 对话框、立绘、输入和文本呈现反馈 | 首阶段完整 Timeline 协调工具 |

候选数据需求：

- 文件：默认语言元信息、块集合及入口规则。
- 节点：类型、源位置、修饰符；文本节点有语言变体；控制流有明确目标。
- 选项：稳定的会话内引用、多语言标签、条件与分支结构。
- 展示输出：内容、说话人信息、实际语言及当前呈现标识。
- 文件完成输出：区别正常完成、停止与错误，供宿主记录文件级进度；具体完成协议待决。

源位置便于试读诊断，不应直接承诺它能作为未来跨修改存档的永久标识。未来逐句恢复需要另行设计稳定身份及外部状态恢复，不要求本阶段实现快照。

## 6. 工程推进顺序

优先级表示依赖关系，不是已承诺工期。全表为建议路线。

| 步骤 | 工作 | 结束条件 |
| --- | --- | --- |
| P0-A | 先确定 E01 的输入／输出与文本门控 | 能明确回答一次点击、文本就绪、next、选择各做什么，无核心演出等待 |

## 8. 下一轮讨论入口

先解决 E01，再冻结 AST 或实现 Parser。建议用同一句话的三个输入阶段讨论：文本正在播放、文本刚播放完、已经出现选择菜单。分别明确玩家点击由谁处理、什么条件下发送 next，以及选择是否使用独立输入。
