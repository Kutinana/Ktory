# Ktory 设计宪章

更新日期：2026-09-26

状态：项目定位与设计原则基线。本文规定要达到的目标，不宣称当前版本已经完成全部实现或验证。

## 1. Ktory 是什么

**Ktory 是一套面向对白驱动游戏的叙事创作与接入系统。作者默认以 `.ktr` 为文本与剧情流程的唯一定义源，通过共享呈现设置、逐句覆盖和显式演出交接组织剧情；配套工具将这些声明绑定到游戏资源与事件，游戏引擎负责具体表现、世界状态和实际事件判定。**

这是产品目标，不是当前功能清单。当前语言与运行时仍按宿主驱动的离散拍协议工作；共享呈现设置、可配置绑定与显式信号依赖属于已确认、待落实的需求，语法与接口尚未冻结，见 [scope](ktory-scope_v1.md)及 [implementation §1.4](ktory-implementation_v1.md#14-2026-09-26-需求修订已确认待落实)。

主要服务独立作者与小型开发团队的对白创作，当前以日系视觉小说式场景为主要参照。线性对白、普通选择及汇流是主要路径；循环调查需要正确支持，但不主导系统复杂度。

产品由语言、纯 C# 核心、独立试读和宿主接入工具共同构成。目标是减少重复声明、逐场景连接代码，以及脚本与演出工具之间重复维护的剧情关系。作者应尽可能只写正文与本句变化，通过资源绑定接入同类演出，主要在 `.ktr` 中调整剧情。

### 术语必须准确

- **拍（Beat）**是逻辑上的内容输出或停止边界，可以是对白或无文本指令。它不等于固定时长、动画片段或一项外部动作的完整生命周期。选择是需要有效提交才能继续的结构边界。
- **宿主驱动**描述当前执行协议：核心收到有效操作后同步处理剧情，不根据现实时间、文字完成百分比或外部动画状态自行决定推进。同步求值不意味着执行整场戏，也不意味着调用必然为常数时间；它不禁止未来记录脚本显式声明的信号依赖。
- **Forward-Only**指运行时不自动撤销已发生的外部副作用。它不禁止向后跳转、循环或重复进入，也不否定以后单独设计逐句恢复。
- **演出意图**包括“在这一拍触发什么”及“后续剧情依赖哪个演出节点或完成信号”。后者是待落实的显式交接目标，也适用于无对白的纯演出段落，不意味着所有演出默认阻塞。动作怎样制作、事件是否发生及跳过后的表现结果仍由宿主落实。
- **Speaker** 的名字声明与呈现资源可以分别维护。Ktory 应允许为说话人关联可选的默认呈现设置，并允许逐句覆盖；这不要求名字、立绘、声音与游戏角色属性成为不可分割的实体。当前 `@speaker` 仍只提供本地化名字与别名，新增关联方式待设计。

共享设置应覆盖名字的多语言映射、默认对话框、默认声音或声音组、表情资源映射。**表情采用“当前句定义 → 适用的全局默认值 → 不展示”的顺序，上一句的局部设置不参与回退。**“不展示”须真正清除旧表情，不能仅不派发新标签。此规则已确认但尚待实现；不自动推广为省略 BGM 即停止音乐。局部明确取消默认值、错误资源名的处理仍待工程决策。

## 2. 为什么不直接用 Ink

Ink 同样支持宿主逐次 `Continue()`、分支选择、一次性与持久选项、标签、外部函数、独立试读和 Unity 集成。不能将“可以控制推进”“可以触发演出”“支持分支”写成 Ktory 独有能力，也不能将 Ink 描述为只能用于文学文本。

Ktory 选择把以下约定直接纳入自己的语言与接入契约：

| 取舍 | 希望减少的工作 |
| --- | --- |
| 结构化对白、无文本指令拍、选择及控制流 | 每个游戏重新定义如何把输出字符串解释成对白与指令 |
| 锚点与带参数的修饰符 | 每个项目自行设计、解析和分发演出元数据格式 |
| 同节点、同文件维护译文，明确回退与无副作用切语言 | 写作者在不同语言脚本、节点和宿主之间手动保持语义对应 |
| 共享呈现默认值与逐句覆盖（待落实） | 逐句重复声明对话框、声音组与表情资源映射 |
| 编辑器绑定与显式演出交接（待落实） | 为同类内容逐场景重复编写监听、暂停、恢复与清理代码 |
| 核心只保留必要叙事执行状态，世界状态归宿主 | 不必要地复制背包、角色属性及演出状态 |
| 试读与游戏共享核心和行为用例 | 在不同工具里重新维护分支、循环和语言选择逻辑 |

这些工作也可以通过 Ink 加项目包装层完成。**Ktory 的理由是将这组特定工作流的约定维护成一个产品；不是证明 Ink 无法做到。** 如果项目主要需要 Ink 已有的叙事表达、状态存读档和工具链，或者已有合适的 Ink 包装层，直接用 Ink 是合理选择。为区别而改变符号、复制功能或扩大范围，不构成立项理由。

差异应体现为把项目自定的对白呈现、资源绑定与演出交接维护成一致、可复用、可验证的产品能力，包括正确匹配本次演出的通知。独立产品的价值由实际工作量减少证明；独立运行时的必要性仍由具体语义与维护成本判断。目前尚不能宣称 Ktory 比 Ink 更成熟、性能更好，或已经减少真实项目的演出接线。

Ink 官方核验依据：[运行与宿主接入](https://github.com/inkle/ink/blob/master/Documentation/RunningYourInk.md)、[语言与选项](https://github.com/inkle/ink/blob/master/Documentation/WritingWithInk.md)、[项目与 Inky](https://github.com/inkle/ink)、[Unity 集成](https://github.com/inkle/ink-unity-integration)。这些资料支持能力事实；上述产品取舍是 Ktory 的设计判断。

## 3. 系统必须保证什么

下列 C01–C08 是设计与验收要求。实现状态和验证证据必须另外记录，不能以本节承诺代替测试。

| 编号 | 必须保证 | 验收含义 |
| --- | --- | --- |
| C01 | 明确且可复现的剧情执行 | 给定同一脚本、入口、初始会话条件、宿主求值结果与操作顺序，规范化后的内容、控制流及标签派发轨迹一致；比较不依赖随机生成的会话 ID |
| C02 | 保留拍与选择边界 | 普通推进不能绕过待选状态；有效选择执行到下一处输出、选择或结束；宿主不能为同一次提交再附加一次推进而跳过分支首拍 |
| C03 | 副作用与展示刷新分开 | 标签在规定的节点进入或选项提交时派发；切语言、刷新 UI 不重放剧情副作用；显式循环重入按规格允许重新派发。此要求不承诺外部系统的事务或跨崩溃 exactly-once |
| C04 | 多语言输出真实 | 保留请求语言，缺译按规则回退，正文报告实际输出语言；名字、对白与选项各自选取译文；不伪造缺译正文，不因切语言改变分支和消费历史 |
| C05 | 单一推进责任与过期输入隔离 | 每个宿主会话明确由谁提交推进；计时、快显、选择、重启与关闭不能让旧输入作用于新呈现。呈现 ID、会话世代和具体拒绝协议需由技术契约明确 |
| C06 | 语法错误与执行失控可诊断 | 不把有歧义的结构静默猜成另一段剧情，不静默丢文本；错误尽可能给出源码位置；无输出循环有执行预算，自动连续推进有批次或调度边界 |
| C07 | 试读宽容与游戏语义分开 | 试读可以忽略未知外部选项条件、跳过未知演出，但不伪造世界状态、不自动执行所有分支；跳过演出不等于外部信号已发生，新增交接的试读策略待定；真实游戏明确提供求值与处理器策略 |
| C08 | 核心复用且验证可追溯 | Core、桥接和宿主使用同一套已确认语义；每项验证注明提交、测试层与环境，不能把模拟器或核心单测当成 Unity 实机证据 |

C04 中选项级实际语言载荷的实现及证据见 implementation §5.3.1；C05 的完整跨会话协议、C06 的全面诊断等仍需按实现规格补齐或明确。各项均不得仅因写入宪章就宣称所有宿主已交付。

## 4. 谁拥有什么

| 对象 | 权威所有者 | 边界 |
| --- | --- | --- |
| 剧情拓扑与当前执行位置 | `.ktr` 加 Ktory 核心会话 | 选择、调用栈、循环上下文、会话内选项消耗由核心维护 |
| 世界状态 | 宿主游戏 | 背包、任务、角色属性、场景实体由宿主读取与修改；核心只通过接口获取必要结果 |
| 文本呈现与时钟 | 宿主／接入层 | 打字机、快显、停留、输入队列与实际计时在接入层；当前演出门控也由接入层处理，新增逻辑依赖另行设计 |
| 演出资源及实际生命周期 | 宿主／演出工具 | 制作镜头、移动与音画；判定并报告真实事件，落实跳过后的结果 |
| 有剧情意义的演出依赖 | 默认由 `.ktr` 声明，配套接入落实绑定 | 等待记录由哪个模块承载、通知如何匹配与触发推进仍待设计；不预先限定在 Sequencer 内或外 |
| 共享呈现设置 | 作者配置与可复用接入工具 | 名字与资源可分开维护；引用、跨文件作用域与存储结构待设计，世界属性仍归宿主 |
| 本地化声明与基本选择规则 | `.ktr` 与核心语言契约 | 字体、换行及目标渲染器富文本适配归表现层 |
| 外部过场主导 | 宿主发起的明确接入流程 | Timeline 可暂管播放时机，无须接管后续对白与分支的组织；宿主直接调用分立段落也是允许的接入方式。复杂交接协议仍待设计 |

“Ktory 是唯一置信源”只能用于它负责的剧情语义与执行状态，不能解释成拥有所有游戏状态。仓库中文档、代码与产物的权威划分见[工作流](ktory-workflow.md)。

推荐工作流尽可能由 `.ktr` 统一组织文本、对白顺序、选择与分支，Timeline 等工具负责具体演出及其节奏，不另行维护重复剧情流程。改变走路速度或抬手过程在演出工具中完成；把对白恢复点从“碰到门把手”改到“门打开”，应能在剧本交接安排中体现。允许宿主指定入口，不要求常规创作把每句拆成外部调用的段落。

`.next`、`.wait`、`.skippable` 的标准语义属于接入契约；解析器保留其声明，Sequencer 不读取墙上时钟。当前位于 Core 程序集的 `PresentationController` 是可复用的接入辅助类，逻辑上仍属于表现策略，不改变这一职责边界。

固定时间表达时间要求，演出信号表达事件要求，两者都允许。意图为“演出完成后继续”时，应优先引用完成信号而非估计时长。现有 `.wait(t)` 仍为最低停留限制，本身不自动推进，不能重解释为事件等待；本次也不恢复原型的统一五阶段阻塞生命周期。

## 5. 明确不负责什么

核心不制作或渲染画面，不替游戏判定外部事件，不定义世界状态，不提供可逆的游戏模拟，也不因一个标签存在而保证外部行为成功。当前核心不发起异步演出等待；这描述现行实现边界，不构成对未来逻辑依赖记录的永久禁令。原生富文本直通及项目表达式方言不承诺跨渲染器、跨宿主自动兼容。

第一阶段不包含：持久化存读档、全量回滚、配音系统、翻译提取回填、Timeline 深度集成、其他引擎适配或完整 IDE。这是阶段边界；逐句恢复与降低演出协调负担等长期方向仍可单独规划。

“核心不负责”与“Ktory 产品永远不提供”必须区分。共享呈现、编辑器绑定和显式交接不自动扩张第一阶段验收；按当前情况选择剧情、交还玩家操作后继续剧情两项需求已记录并延期，也不扩张为完整任务系统或通用游戏状态机。

## 6. 当前目标与工作方式

当前已有另一设备上的 Unity 接入工程，该工程及其本地 Ktory 副本不在本工作区。当前设备优先使核心的正确性、首阶段契约覆盖及鲁棒性持续可验证；另一设备提供真实 Unity 接入反馈。不得由仓库中未见游戏场景推断用户未接入 Unity，也不以复制完整游戏工程为核心工作的前置条件。

第一阶段的最终使用基线仍是：同一脚本内写作与翻译，独立试读分支，再由 Unity 展示对白、选择与立绘。分工变化不取消真实游戏验收，只把它作为可追溯的反馈环节。

工作优先级：

1. 将已确认条款映射到行为用例，解决规范、实现与测试冲突。
2. 补齐正常写作、控制流组合、语言刷新和输入时序的自动回归；错误输入不能静默改变作者意图。
3. 用同一源提交构建桥接与分发包，交给另一设备验证，反馈先缩减为本机可运行用例。
4. 根据真实反馈完善通用接入；只有已有需求无法满足时才扩大语言或产品范围。

配套工具应让作者通过编辑器选择资源、绑定对象与脚本声明；新增同类演出主要通过内容和配置完成。新增一种游戏能力可能需写一次接入代码，复用该能力的剧情不应再各写一套。真实节点仍需演出制作者标注；目标是减少重复的监听、暂停、恢复与清理，不承诺所有游戏行为零代码或零配置，通用事件机制保留为扩展方式。

新增功能建议先做默认呈现，再设计绑定与信号交接，先验证“播放一个演出，完成后继续”，再扩展到中途节点。此顺序是工程建议，不是新增的阶段交付承诺；两项后续剧情能力继续延期，现有核心正确性与回归工作继续。具体验收素材与证据要求见[工作流](ktory-workflow.md#新增目标的代表性验证场景待落实)。

评估独立维护 Ktory 的收益时，使用同一个代表性场景与已有的 Ink 包装方案比较：作者需要多少额外标记、新增同类场景需要多少专用宿主代码、多语言切换是否需要额外对齐、故障能否脱离游戏复现。若收益只剩符号偏好，应重新评估自有运行时的维护成本；不得为了维持差异而改变已经明确的所有权边界。

## 7. 文档权威与变更规则

- 本文回答身份、设计目标与职责边界；[scope](ktory-scope_v1.md)记录阶段需求和确认历史。
- [implementation](ktory-implementation_v1.md)仍是第一阶段具体语法、控制流与协议的唯一技术基准。本文不通过概括句暗改某个已确认行为；冲突必须显式记录并同步修订相关条款与测试。
- [workflow](ktory-workflow.md)规定仓库分工、验证和跨设备交付；[engineering](ktory-engineering_v1.md)及 [origin](ktory-origin.md)中的历史候选不能覆盖当前基线。
- README、AGENT.md 与门户各语言页面是上述文档的摘要和入口，不独立发明产品承诺；规范变化在同一次变更中更新有关摘要、样例与测试。
- 每个设计改动应回答：服务哪个实际场景、满足 C01–C08 哪条要求、影响哪层所有权、如何验证。未决事项保持未决；本轮需求批准不等于批准某种异步屏障、信号 API、变量系统或新 AST。

## 8. 讨论来源与本次收束

本轮同时落实共享呈现目标及表情省略规则、编辑器绑定方向和两项延期剧情需求。原型的统一异步生命周期未重新获批，新语法与承载模块未冻结；两设备分工、单一核心和首阶段验收范围保持既有约定。
