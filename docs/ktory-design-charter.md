# Ktory 设计宪章

更新日期：2026-09-26

状态：项目定位与设计原则基线。本文规定要达到的目标，不宣称当前版本已经完成全部实现或验证。

## 1. Ktory 是什么

**Ktory 是一套对白优先、由宿主驱动的按拍叙事脚本语言与运行时。作者在同一份剧本中组织对白、选择、多语言文本及演出意图；核心决定当前剧情内容和控制流，宿主决定如何呈现，以及何时请求继续。**

主要服务独立作者与小型开发团队的对白创作，当前以日系视觉小说式场景为主要参照。线性对白、普通选择及汇流是主要路径；循环调查需要正确支持，但不主导系统复杂度。

产品由语言、纯 C# 核心、独立试读和宿主接入工具共同构成。它的价值应以“写作、试读、放入实际游戏需要多少额外约定和接线”衡量。

### 术语必须准确

- **拍（Beat）**是逻辑上的内容输出或停止边界，可以是对白或无文本指令。它不等于固定时长、动画片段或一项外部动作的完整生命周期。选择是需要有效提交才能继续的结构边界。
- **宿主驱动**指核心收到有效操作后同步处理剧情，不根据现实时间、文字完成百分比或外部动画状态自行决定推进。同步求值不意味着执行整场戏，也不意味着调用必然为常数时间。
- **Forward-Only**指运行时不自动撤销已发生的外部副作用。它不禁止向后跳转、循环或重复进入，也不否定以后单独设计逐句恢复。
- **演出意图**是“在这一拍触发什么”的声明。动作怎样制作、何时完成、是否允许跳过，由宿主实现；标签本身不会让资源或处理器凭空存在。
- **Speaker**是一组可反查的本地化显示名，可有简短别名。它不自动关联立绘、声音、属性或完整角色实体。

## 2. 为什么不直接用 Ink

Ink 同样支持宿主逐次 `Continue()`、分支选择、一次性与持久选项、标签、外部函数、独立试读和 Unity 集成。不能将“可以控制推进”“可以触发演出”“支持分支”写成 Ktory 独有能力，也不能将 Ink 描述为只能用于文学文本。

Ktory 选择把以下约定直接纳入自己的语言与接入契约：

| 取舍 | 希望减少的工作 |
| --- | --- |
| 结构化对白、无文本指令拍、选择及控制流 | 每个游戏重新定义如何把输出字符串解释成对白与指令 |
| 锚点与带参数的修饰符 | 每个项目自行设计、解析和分发演出元数据格式 |
| 同节点、同文件维护译文，明确回退与无副作用切语言 | 写作者在不同语言脚本、节点和宿主之间手动保持语义对应 |
| 核心只保留必要叙事执行状态，世界状态归宿主 | 不必要地复制背包、角色属性及演出状态 |
| 试读与游戏共享核心和行为用例 | 在不同工具里重新维护分支、循环和语言选择逻辑 |

这些工作也可以通过 Ink 加项目包装层完成。**Ktory 的理由是将这组特定工作流的约定维护成一个产品；不是证明 Ink 无法做到。** 如果项目主要需要 Ink 已有的叙事表达、状态存读档和工具链，或者已有合适的 Ink 包装层，直接用 Ink 是合理选择。为区别而改变符号、复制功能或扩大范围，不构成立项理由。

目前可以清楚回答 Ktory 的定位；目前尚不能宣称它已经比 Ink 更成熟、性能更好，或已经减少了真实项目的演出接线。后者必须通过相同场景的实际使用反馈证明。

Ink 官方核验依据：[运行与宿主接入](https://github.com/inkle/ink/blob/master/Documentation/RunningYourInk.md)、[语言与选项](https://github.com/inkle/ink/blob/master/Documentation/WritingWithInk.md)、[项目与 Inky](https://github.com/inkle/ink)、[Unity 集成](https://github.com/inkle/ink-unity-integration)。这些资料支持能力事实；上述产品取舍是 Ktory 的设计判断。

## 3. 系统必须保证什么

下列 C01–C08 是设计与验收要求。实现状态和验证证据必须另外记录，不能以本节承诺代替测试。

| 编号 | 必须保证 | 验收含义 |
| --- | --- | --- |
| C01 | 明确且可复现的剧情执行 | 给定同一脚本、入口、初始会话条件、宿主求值结果与操作顺序，规范化后的内容、控制流及标签派发轨迹一致；比较不依赖随机生成的会话 ID |
| C02 | 保留拍与选择边界 | 普通推进不能绕过待选状态；有效选择执行到下一处输出、选择或结束；宿主不能为同一次提交再附加一次推进而跳过分支首拍 |
| C03 | 副作用与展示刷新分开 | 标签在规定的节点进入或选项提交时派发；切语言、刷新 UI 不重放剧情副作用；显式循环重入按规格允许重新派发。此要求不承诺外部系统的事务或跨崩溃 exactly-once |
| C04 | 多语言输出真实 | 保留请求语言，缺译按规则回退，正文报告实际输出语言；名字、对白与选项各自选取译文；不伪造缺译正文，不因切语言改变分支和消费历史 |
| C05 | 单一推进责任与过期输入隔离 | 每个宿主会话明确由谁提交推进；计时、快显、选择、重启与关闭不能让旧输入作用于新呈现。呈现 ID、会话世代和具体拒绝协议需由技术契约明确 |
| C06 | 语法错误与执行失控可诊断 | 不把有歧义的结构静默猜成另一段剧情，不静默丢文本；错误尽可能给出源码位置；无输出循环有执行预算，自动连续推进有批次或调度边界 |
| C07 | 试读宽容与游戏语义分开 | 试读可以忽略未知外部选项条件、跳过未知演出，但不伪造世界状态、不自动执行所有分支；真实游戏明确提供求值与处理器策略 |
| C08 | 核心复用且验证可追溯 | Core、桥接和宿主使用同一套已确认语义；每项验证注明提交、测试层与环境，不能把模拟器或核心单测当成 Unity 实机证据 |

C04 中选项级实际语言载荷、C05 的完整跨会话协议、C06 的全面诊断等仍需按实现规格补齐或明确；不得仅因写入宪章就宣称已交付。

## 4. 谁拥有什么

| 对象 | 权威所有者 | 边界 |
| --- | --- | --- |
| 剧情拓扑与当前执行位置 | `.ktr` 加 Ktory 核心会话 | 选择、调用栈、循环上下文、会话内选项消耗由核心维护 |
| 世界状态 | 宿主游戏 | 背包、任务、角色属性、场景实体由宿主读取与修改；核心只通过接口获取必要结果 |
| 文本呈现与时钟 | 宿主／接入层 | 打字机、快显、停留、输入队列、演出门控与实际计时在接入层 |
| 演出资源及生命周期 | 宿主／演出工具 | 镜头、移动、音画实现、完成判定、跳过后状态落实不进入核心执行等待 |
| 本地化声明与基本选择规则 | `.ktr` 与核心语言契约 | 字体、换行及目标渲染器富文本适配归表现层 |
| 外部过场主导 | 宿主发起的明确接入流程 | 宿主可决定调用段落与投递操作的时机；不另写一个与核心争夺同一分支状态的播放器。复杂交接协议仍属后续设计 |

“Ktory 是唯一置信源”只能用于它负责的剧情语义与执行状态，不能解释成拥有所有游戏状态。仓库中文档、代码与产物的权威划分见[工作流](ktory-workflow.md)。

`.next`、`.wait`、`.skippable` 的标准语义属于接入契约；解析器保留其声明，Sequencer 不读取墙上时钟。当前位于 Core 程序集的 `PresentationController` 是可复用的接入辅助类，逻辑上仍属于表现策略，不改变这一职责边界。

## 5. 明确不负责什么

核心不制作或渲染画面，不管理外部动作等待，不替游戏定义世界状态，不提供可逆的游戏模拟，也不因一个标签存在而保证外部行为成功。原生富文本直通及项目表达式方言不承诺跨渲染器、跨宿主自动兼容。

第一阶段不包含：持久化存读档、全量回滚、配音系统、翻译提取回填、Timeline 深度集成、其他引擎适配或完整 IDE。这是阶段边界；逐句恢复与降低演出协调负担等长期方向仍可单独规划。

“核心不负责”与“Ktory 产品永远不提供”必须区分。配套工具可以提供输入路由、对话框或常见演出绑定，只要不把宿主职责重新塞进 Sequencer。

## 6. 当前目标与工作方式

当前已有另一设备上的 Unity 接入工程，该工程及其本地 Ktory 副本不在本工作区。当前设备优先使核心的正确性、首阶段契约覆盖及鲁棒性持续可验证；另一设备提供真实 Unity 接入反馈。不得由仓库中未见游戏场景推断用户未接入 Unity，也不以复制完整游戏工程为核心工作的前置条件。

第一阶段的最终使用基线仍是：同一脚本内写作与翻译，独立试读分支，再由 Unity 展示对白、选择与立绘。分工变化不取消真实游戏验收，只把它作为可追溯的反馈环节。

工作优先级：

1. 将已确认条款映射到行为用例，解决规范、实现与测试冲突。
2. 补齐正常写作、控制流组合、语言刷新和输入时序的自动回归；错误输入不能静默改变作者意图。
3. 用同一源提交构建桥接与分发包，交给另一设备验证，反馈先缩减为本机可运行用例。
4. 根据真实反馈完善通用接入；只有已有需求无法满足时才扩大语言或产品范围。

长期目标是减少每个场景反复维护信号、监听、暂停与恢复配对的负担。当前不宣称已实现完整演出协调；新增能力必须说明它减少了哪项重复工作、由哪一层负责，并提供可验收场景。

评估独立维护 Ktory 的收益时，使用同一个代表性场景与已有的 Ink 包装方案比较：作者需要多少额外标记、新增同类场景需要多少专用宿主代码、多语言切换是否需要额外对齐、故障能否脱离游戏复现。若收益只剩符号偏好，应重新评估自有运行时的维护成本；不得为了维持差异而改变已经明确的所有权边界。
