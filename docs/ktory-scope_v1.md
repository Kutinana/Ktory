# Ktory：Scope 与设计决策

更新日期：2026-09-24  
阶段：规划中；尚未进入实施  
依据：本项目 scope 讨论及原版 `ktory.md`

## 1. 文档用途与维护约定

本文件持续记录当前已确认的目标、责任边界、设计决策与未决问题。后续对话形成新结论或修订既有结论时，更新同一份文档，并记录变更理由。讨论中的建议不得直接记为已确认决策。

原版 `ktory.md` 保留为初始方案参考。它含有具体语法、AST 与调度设计，不应据此认定所有技术细节已经定案。若新确认的 scope 与原版方案冲突，以新确认的决策为后续修订依据。技术规格与 scope 的全面对齐尚未进行。

维护发生在协作对话中，不依赖后台自动监听。继续讨论时先依据当前文档；遇到矛盾明确记录并解决，不静默覆盖。

## 2. 当前定位

主要创作参照是用户偏好的日系视觉小说。带历史记录的反复询问和循环选择是低频需求；它们需要支持，但不应作为主导系统复杂度的典型场景。不能仅根据这一风格偏好推定存读档、回滚、已读跳过等功能已被要求。

Ktory 是以对白为中心的游戏叙事脚本与运行时系统。剧本承载对白、交互及演出触发；具体演出在宿主引擎或演出工具中制作。演出对推进的限制在游戏侧配置和判定，由游戏决定何时向 Ktory 发送 next。完整叙事的实现由脚本与游戏侧配置共同构成，不要求脚本独自描述所有演出同步条件。

默认情况下，Ktory 是唯一置信源。同时，系统应支持由外部演出系统主导的过场。具体引擎、表现形式和是否采用 Timeline 均不是定位前提。

“唯一置信源”已确认作为原则；它对叙事流程、游戏世界状态和局部演出状态各自意味着什么，尚需明确，不能直接推导成所有游戏状态都由 Ktory 保存。

## 3. 已确认的决策

### 第一阶段验收基线（已确认）

用户确认：独自编写含对白、选择和演出触发的脚本，在同一文件维护译文，脱离 Unity 试读分支，再将同一脚本用于 Unity，足以开始实际项目使用。Unity 首阶段只需对话框与立绘显示，不要求实现 Timeline 集成或演出推进限制。独立试读器至少提供语言选择。

这一基线收窄的是第一阶段交付，不撤销此前确定的长期演出协作目标。Scope 初步收束，后续工作应将该基线转为一致的语言和运行时契约，而非继续无边界增加首阶段功能。

| 编号 | 决策 | 理由或边界 |
| --- | --- | --- |
| D01 | 先定义目标与 scope，再判断具体修改的必要性。 | 项目尚在规划，任何设计均可调整；实施优先级应由目标决定。 |
| D02 | Ktory 以对白为中心，并允许编剧表达完整的叙事与演出意图。 | 完整表达不等于所有演出细节都必须在文本里制作。 |
| D03 | 不以完全替代 Timeline 等演出工具为目标。 | 坐标、轨迹、实时演算动画等内容在可视化环境中制作和测试更直观。 |
| D04 | Ktory 必须能够指示演出系统何时触发镜头移动、人物移动等行为。 | 对白与演出的节奏关系属于核心需求，不能仅依靠彼此独立的播放。 |
| D05 | Ktory 与演出端需要双向通信。 | 除发出指令外，还需要演出端反馈，以协调叙事过程。具体事件和协议未定。 |
| D06 | 默认情况下，Ktory 是唯一置信源。 | 外部演出的接入形式不应改变系统的默认定位；权威范围仍需细化。 |
| D07 | 支持外部演出系统主导的过场。 | 用户明确要求：既然需要双向通信，也应支持这种协作方式。具体交接机制未定。 |
| D08 | 不绑定 Unity、Timeline 或某一种表现层实现。 | Timeline 是讨论中的具体例子；其他引擎和演出方案同样应可接入。 |
| D09 | 常见对白与演出协作不应要求作者反复手动布置信号、编写监听，并在脚本中配对 pause/continue。 | 用户结合 Ink 与 Timeline 的经验明确提出这一痛点。双向通信本身不足以满足目标，还必须降低逐场景协调的创作负担。 |
| D10 | Ktory 默认关注文本是否完成播放，文本播放完成时文本门控开启。 | 不应将此前特定情景中的等待移动完成推广为所有演出的隐式门控条件。开启门控与自动推进需区分。 |
| D11 | 脚本可声明当前台词的播放行为，包括点击快显的限制。 | 用户示例 `.skippable(false, 3)` 表示该句出现后的前三秒不能通过点击立即显示全文；不等于跳过外部演出。完整参数规则未定。 |
| D12 | 获得钥匙等剧情结果默认写在 Ktory 脚本，也允许项目在外部演出端实现。 | 不强制所有状态修改均通过 Ktory；跳过时如何确保结果正确仍待设计。 |
| D13 | 脚本不采用异步等待演出反馈的执行模型，不在脚本中显式等待某次演出完成。 | 此前提出的脚本引用执行实例并等待完成方案不采用。运行时底层是否使用异步技术不是本条决定的内容。 |
| D14 | 演出造成的推进限制由游戏侧落实：条件满足时，游戏向 Ktory 播放器发送 next。 | 例如角色到门口后才发送 next；角色未到达不应成为 Ktory 内部的演出等待状态。文本门控与外部 next 发送条件分别考虑。 |
| D15 | 演出是否限制推进以及限制条件，在游戏侧的编辑器或绑定配置中声明，不采用脚本演出修饰符声明该策略的方案。 | “演出结束”没有统一适用的含义；例如只要求前三秒不可跳过，之后即可跳过。条件最终由表现层实现和验证，Ktory 不负责判定其成立。具体编辑器设计未定。 |

## 4. 创作责任边界

### 调查交互的组织方式与优先级

- 对纯文本调查中的“问过某话题”等叙事记录，用户认为没有必要下放到游戏侧，同时认可这会增加 Ktory 的内部状态复杂度。记录形式、作用域和持久化方式未定，不据此确认完整通用变量系统。
- 此类情景及循环选择在用户创作中较少见。此前“当前阶段充分支持脚本组织调查”的要求保留，但不等于循环调查是首阶段的主要体验或最复杂状态系统的设计依据。

- 脚本组织调查、游戏组织调查两种方式都需要支持，适应不同游戏的交互模式。
- 当选项间的差异主要体现在文本与叙事分支上时，由脚本组织调查；当单个选项需要处理大量额外游戏逻辑时，可以由游戏组织调查并调用 Ktory 段落。这是选用倾向，不是禁止脚本调用游戏逻辑的硬性分界。
- 当前阶段要求充分支持脚本组织调查。这一优先级不等于要求首阶段完成游戏组织调查所涉及的全部复杂场景；后者具体阶段范围未定。
- 原版的循环选择与容器可以作为候选方案，但本次决定不自动确认其语法、插件机制或状态存储方式。

### 阶段范围：核心与引擎接入

- 引擎配套工具属于必要的交付方向，但不作为第一阶段的主要开发重点。
- 第一阶段同步实现 Unity 接入工具，用于在真实编辑器中测试 Ktory 的表现，并以接入实践验证核心设计。
- 其他引擎的接入暂不考虑开发；核心不绑定特定引擎的原则保留，不据此提前建设多引擎适配。
- Unity 首阶段接入支持对话框和立绘显示即可满足用户使用；Timeline 集成与演出推进限制不作为首阶段验收要求。具体配置界面未定，不承诺完整可视化编辑器或全部预设策略。

### 阶段范围：独立试读

- 第一阶段需要能够脱离 Unity 试读 Ktory 脚本，不以启动游戏编辑器为前提。
- 试读器至少支持语言选择，这是首阶段必要能力；切换时是否立即刷新当前句的细节未定。
- 工具形态候选为 Web 端或 VS Code 插件，用户目前认为 VS Code 插件可能更方便；尚未最终选型，也未要求同时实现两端。
- 本次确认的是独立试读能力，不自动扩大为完整 IDE、演出预览器、热更新或完整编辑器插件功能。
- 第一阶段试读器直接跳过所有不能解析为基础行为的内容，不要求外部状态模拟、测试值配置或外部演出的实际播放。此前提出的外部依赖模拟方案不纳入首阶段要求。
- 遇到无法求值的外部选项条件时，忽略该条件，全部展示选项，供作者选择试读；不隐藏受其控制的选项，也不模拟外部状态。“基础行为”的准确集合尚需定义；本决定不要求忽略可正常求值的基础条件，不代表自动执行所有分支。
- 独立试读不验证 Unity 中的实际演出、外部状态或推进限制；试读通过不等于这些外部行为已得到验证。

### 阶段范围：多语言与配音

- 多语言是刚需，纳入第一阶段必要能力，不能以单语言实现作为阶段目标的替代。
- Ktory 输出给表现层时需要标明实际输出语言。请求英文但回退中文时，语言标识为 `zh`；请求语言与实际文本语言不混同。具体载荷字段未定。
- 请求语言缺少某句译文时，回退文件默认语言；用户确认 `defaultLang = zh` 且缺少英文译文时直接显示中文，不以缺译提示替代正文。试读器的额外缺译提示不是已确认的首阶段要求。
- 文件级 `defaultLang` 用于上述回退；其声明语法、是否必填、未标注文本归属及未指定播放语言时的默认选择仍待明确。默认语言文本也不存在的异常处理暂未定义。
- 配音支持暂不考虑，不作为第一阶段验收要求；这不取消已讨论的通用演出触发或音效接入方向。
- 第一阶段以同一 `.ktr` 文件内维护多语言变体为主要工作流。用户通常独自完成写作与翻译，这种方式足够满足当前使用需要。
- 暂不提供译文提取、回填、独立翻译表或翻译协作工具。允许使用者自行维护多个语言版本的 `.ktr` 文档，但不据此承诺版本之间的自动同步、对齐或一致性维护。
- 常规缺译回退已确认；语言切换时机和具体本地化覆盖范围仍保留为设计问题，不从“多语言刚需”自动推导完整本地化生产管线。

### 阶段范围：进度持久化与恢复

- 第一阶段可以不提供存读档能力，也不要求 Ktory 持久保存文件内播放进度。
- 文件级进度可由游戏记录最后一个完成播放的 `.ktr` 文件，作为阶段性方案；不要求 Ktory 自行维护跨会话播放进程。
- 最终目标是支持逐句恢复，具体阶段、接口和恢复范围尚未确定。画面、演出、音频时间点的恢复精度，以及全量回滚，不因这一目标自动纳入。
- 这里的“不记录播放进程”指无需持久化和恢复文件内进度，不取消正常播放所需的当前执行位置或会话内叙事记录。
- 文件完成记录能够表示粗粒度进度，但不能一般性地替代分支选择、背包等状态的保存；这些状态如何跨文件、跨会话处理留待后续定义，不以此要求首阶段增加存档系统。

### 已确认的方向

- 演出推进条件与演出自然结束相互独立：到达某位置、播放前三秒等都可以成为游戏侧条件，不要求统一抽象为“演出完成”。
- 游戏侧配置演出推进限制，不影响脚本声明文本自身的播放行为，例如 D11 的文本快显限制。两种“三秒”分别约束演出与文本，不能混同。

- Ktory 承担对白创作与叙事编排，并能决定何时触发演出。
- 镜头、角色运动等具体演出可以在 Timeline 或其他宿主工具中制作。
- 剧本写出一个动作，不等于引擎已经具备识别、实现和验证该动作的能力。资源制作及其与脚本的关联是必须面对的工作。
- 音乐、音效可以放在脚本或演出工具中，依据场景需要选择；用户倾向于用脚本更直接地把握声音节奏。
- 镜头通常与场景和动画配合更紧密，用户优先考虑在演出工具中制作。这是创作偏好，不是禁止脚本触发镜头的规则。

### 用于检验边界的场景

艾莉丝说话时走向门口；走到一半，爆炸打断台词；镜头转向窗外；声音结束后，玩家选择继续追问或离开。

用户希望整段叙事都可以写进剧本，但不希望因此被迫用文本定义和测试所有坐标与运动细节。

“走到一半”如何由游戏侧可靠识别仍未定。识别结果可用于游戏侧决定何时发送 next，不采用脚本等待该反馈的方案。“一半”不能擅自解释为时间或路程的 50%。

### 已确认的情景：对白与移动同时进行

艾莉丝说“门外有人，我去看看”，同时开始约四秒的走向门口演出；下一句“奇怪，什么都没有”发生在到达之后。本情景的点击表示确认对白，暂不讨论打字机快显。

用户确认在该同步情景下以下默认行为及两种可选行为均需支持。后续澄清：Ktory 的一般默认门控只关注文本播放完成，不自动等待演出；下面的演出同步行为由游戏侧控制 next 的发送实现，不是脚本内部的等待。如何配置这种配合且避免逐场景样板代码仍需设计。

| 行为 | 玩家在移动完成前确认 | 移动先完成 |
| --- | --- | --- |
| 默认：各自确认、条件汇合 | 保留当前对白的确认；等移动完成后自动进入下一句，无需重复点击。 | 等玩家确认当前对白后继续。 |
| 可选：点击跳过当前演出 | 跳过剩余过程，直接从到门口之后的场景继续播放。 | 依当前段落的推进规则继续。 |
| 可选：演出完成前点击无效 | 提前点击不保留；演出完成后需要再次确认。 | 等玩家确认后继续。 |

若有多个需要确认的断点，各自确认。本次确认不构成对后续多个断点的一次性确认。默认等待不意味着暂停所有表现：待机和环境声音等可继续。

跳过当前演出的终点、场景状态如何落实，以及中途事件是否执行尚未确定。“跳过”不能未经讨论推广为跳过整个剧情、所有断点或玩家选择。

## 5. 尚未确定的范围与设计

### 已确认的创作痛点与验收方向

用户报告：在其 Ink 与 Timeline 整合实践中，需要放置大量 eventSignal，让解释器监听，并在对白期间暂停 Timeline，在脚本中手动指定暂停与继续。Ktory 应避免重复这一体验。这是用户实践的记录，不是对 Ink 所有集成方式的结论。

因此，“支持双向通信”只是能力要求，“常见配合无需逐处手写协调”是独立的作者体验要求。减少样板协调不能以限制原有叙事表达目标为代价。

候选验收场景（待确认）：外部演出到达对白段落后，玩家阅读或选择，结束后演出继续；作者不必分别维护事件标记、监听逻辑及成对的暂停与恢复命令。对应工具和运行时如何实现尚未决定。

需要区分具有叙事意义的特殊同步节点与纯粹用于连接两个播放器的重复操作。文本播放完成开启文本门控已确认；哪些演出应继续、哪些需要额外等待，以及交互确认与演出完成的组合仍待设计。不能直接假定“每句对白暂停整条 Timeline”。

### 演出结束边界：问题与候选方案

用户指出：脚本只记录演出触发，不记录结束点；如果要求演出端正确结束，结束边界从哪里来？不能将逐段标记所有起止点的负担隐藏在“演出端负责”中。

此前候选方案让脚本引用演出执行实例并等待其完成；用户已明确不采用这种脚本模型。游戏侧仍需识别演出完成或到达某个节点，决定何时发送 next。是否在游戏接入层使用执行实例、资源边界或片段标记尚未确定，不要求 Ktory 脚本维护结束点。

自然播放完成、点击快显文本、跳过演出并落实结果是不同能力。外部接入层能否正确完成跳过及其中状态修改，需要单独约定，不能仅靠“有结束时间”推导。

### 后续讨论顺序

已确认 next 的演出相关发送条件放在游戏侧配置；引擎配套工具必要，首阶段同步开发 Unity 接入以进行真实编辑器验证，其他引擎暂不开发。接入工具的具体完整度未定。后续先界定对白之外的应用范围，再细化首阶段验收场景。文本快显、玩家确认、演出条件与自动推进的输入归属，以及原版 `.next(waitTime)` 如何与外部推进限制组合，保留为后续设计问题。

按依赖关系继续讨论，避免提前细化底层规范：

1. **权威与控制权边界**：唯一置信源具体覆盖什么？外部演出主导一段过场时，谁决定局部推进、分支和返回？如何与 D06 一致？
2. **最小协作能力**：对白与移动并行时的默认确认行为及两种可选行为已确认，见第 4 节。继续明确跳过后的状态、特殊节点、打断与恢复等能力的范围；具体协议未定。
3. **应用范围**：两种调查组织方式都需要，当前阶段充分支持脚本组织调查；纯叙事记录无需下放游戏侧，但循环选择低频。第一阶段不要求存读档，游戏可记录文件完成进度；最终支持逐句恢复。状态的作用域、具体持久化方案及更广泛的探索和任务流程仍未定。
4. **作者与验证流程**：第一阶段需独立于 Unity 试读，Web 或 VS Code 插件选型未定，目前偏向后者。只执行基础行为，其余跳过；无法求值的外部选项条件忽略，全部选项展示。不要求模拟外部依赖；基础行为清单、编辑辅助和资源绑定的具体功能未定。
5. **首版范围及技术方案**：多语言为首阶段刚需，以同文件语言变体维护；允许用户手工维护多份语言版本，翻译提取回填工具与配音暂缓。在范围收敛后，再决定脚本语法、AST、状态模型和接口。

## 6. 原方案中暂不视为定案的内容

原版中的 Forward-only、Anchor/Decorator 模型、插件化容器、具体跳转规则、五阶段生命周期和 canAdvance 门禁，均保留为待评估方案。没有因本次讨论而自动批准或否决。

与 Ink 的关系也尚未定论。先依据目标判断现有工具是否满足需求，再讨论独立系统的必要性；不把“必须与 Ink 不同”作为已确认目标。

## 7. 决策记录

### 2026-09-24：建立 scope 文档

- 汇总规划阶段的目标优先原则和对白中心定位。
- 记录文本叙事编排与可视化演出制作之间的责任边界。
- 确认双向通信、默认由 Ktory 作为唯一置信源、支持外部演出主导过场，以及不绑定具体引擎或 Timeline。
- 保留唯一置信源的准确范围与控制权交接机制为下一步问题。
- 建立随协作对话更新同一文档的维护约定。

### 2026-09-24：补充对白与演出的协作体验目标

- 新增 D09：避免大量信号、监听与手写 pause/continue 成为常见创作流程。
- 明确双向通信是必要能力，但不能据此认定易用性目标已经满足。
- 将自动协调的验收场景及暂停范围列为候选和未决项，未提前确定接口或语法。

### 2026-09-24：确认并行对白与演出的推进方式

- 默认保留当前断点的确认，等待该段所需条件满足后继续；多个断点分别确认。
- 支持点击直接跳过当前演出，以及演出完成前点击无效两种可选行为。
- 下一候选情景：跳过一段含开门、拾取钥匙等状态变化的演出时，正确结果由谁定义和落实；尚未作出决策。

### 2026-09-24：澄清文本门控与演出边界

- 新增 D10–D12：默认文本门控、台词点击快显控制、剧情结果默认位于脚本但允许外部实现。
- 收窄此前同步情景的默认规则，避免误读为任何演出都会阻止对白推进。
- 记录演出结束边界从何而来的问题及候选方案；尚未确认执行实例、片段标记或跳过实现。

### 2026-09-24：将演出同步职责明确放到游戏侧

- 新增 D13–D14：脚本不显式异步等待演出；游戏决定何时向播放器发送 next。
- 不采用此前的脚本等待执行实例方案，并修订相关情景表述。
- 保留文本门控要求；演出未完成本身不再构成 Ktory 内部的等待条件。
- 下一问题聚焦游戏侧协作配置的作者体验，防止重新引入手工信号接线负担。

### 2026-09-24：确认推进策略在外部配置

- 新增 D15，采用游戏侧配置方向，不采用脚本演出修饰符声明推进限制的建议。
- 明确允许推进的条件不必是演出结束，例如播放前三秒后允许跳过剩余过程。
- 修订当前定位，避免“完整叙事表达”被误解为所有演出配合规则必须写进脚本。
- 保留游戏侧接入组件与编辑器工具是否属于 Ktory 交付范围为下一 scope 问题。

### 2026-09-24：确定首阶段的 Unity 接入范围

- 引擎配套工具必要，但不是首阶段开发重心；Unity 接入工具与首阶段同步实现，用于真实编辑器测试。
- 其他引擎暂不开发；保留核心引擎无关原则。
- 接入工具的功能完整度与验收标准尚未确定。

### 2026-09-24：确认调查组织方式与优先级

- 两种方式均需支持：以文本差异为主时适合脚本组织，额外游戏逻辑较多时倾向游戏组织。
- 当前阶段要求充分支持脚本组织调查。
- 不据此预先确认容器实现或状态系统；游戏组织调查的阶段完整度仍待明确。

### 2026-09-24：校准主要创作场景与叙事状态范围

- 用户创作习惯偏向日系视觉小说，循环选择很少出现。
- 纯叙事历史记录无需下放游戏侧；内部状态复杂度是需控制的成本。
- 保留脚本调查支持要求，但后续 scope 讨论不再以复杂循环调查为主要代表情景。
- 存读档、回滚等常见视觉小说能力尚未据此确认，需分别讨论。

### 2026-09-24：划分进度恢复的阶段目标

- 第一阶段无需存读档，可由游戏仅记录最后完成的 `.ktr` 文件。
- 逐句恢复确认为最终目标，暂不指定交付阶段与外部表现恢复精度。
- 区分运行时执行状态与持久化进度，不因暂缓存档而取消会话内状态支持。

### 2026-09-24：确认独立试读为首阶段能力

- 第一阶段必须支持脱离 Unity 试读。
- 候选形态为 Web 端或 VS Code 插件，偏向后者，但尚未锁定或要求双端交付。
- 外部依赖的模拟程度及编辑辅助范围保留为后续问题。

### 2026-09-24：收窄首阶段试读器范围

- 用户明确要求直接跳过所有不能解析为基础行为的内容。
- 不纳入此前建议的外部状态模拟和测试值配置。
- 仅保留未知条件下的内容处理边界为待明确问题，不将试读器扩展为游戏模拟器。

### 2026-09-24：确认未知选项条件的试读行为

- 忽略无法求值的外部条件，全部展示选项供试读，不跳过整个选项。
- 本规则限于试读环境，不改变游戏运行时条件语义，也不代表所有分支自动执行。

### 2026-09-24：确认多语言与配音优先级

- 多语言确认为刚需，列入第一阶段。
- 配音暂不考虑；翻译工作流和语言变体组织方式仍待讨论。

### 2026-09-24：确定多语言创作工作流

- 用户独自写作与翻译，以同一 `.ktr` 内维护多语言即可满足当前需求。
- 暂不要求翻译内容提取与回填工具。
- 允许使用者自行维护多个语言版本的 `.ktr`；不承诺自动同步或一致性维护。

### 2026-09-24：确认首阶段验收基线并补充语言输出要求

- 用户确认所述创作流程足以投入使用，并进一步收窄 Unity 验收到对话框与立绘显示。

- 文件级 `defaultLang` 作为候选方案记录，其默认与回退语义尚待定义。

### 2026-09-24：确认缺译时回退默认语言

- 在默认中文、请求英文但缺少英文译文的情景中，直接回退显示中文。

- 不将额外缺译提示列为首阶段必需功能。
