# Ktory：Scope 与设计决策

更新日期：2026-10-22

阶段：既有核心／试读器继续维护；Main／辅助重设计已确认并授权实施，验证进行中；另一设备已有 Unity 接入

依据：scope 讨论、现行实现规格、2026-09-26 的设备与工作流说明，以及「分析漏洞与Ink区别」「Ktory 多轨编排」需求修订与本次文档落实请求

> 统一原则：Ktory 是面向对白驱动游戏的叙事创作与接入系统。当前运行时支持宿主驱动的单轨／多轨按拍协议及主／副语言输出；本轮实现状态与验收证据单独追踪；文件内 speaker 默认修饰符与覆盖已实现；跨文件共享、可配置绑定与显式信号依赖仍待落实。定位、与 Ink 的边界、必须保证的行为及非目标以[设计宪章](ktory-design-charter.md)为准；具体技术条款以[实现规格](ktory-implementation_v1.md)为准；设备分工见[工作流](ktory-workflow.md)。下文只保留当前目标、已确认边界和真实未决事项。

## 1. 文档用途与维护约定

本文件维护当前已确认的目标、责任边界与未决问题。形成新结论时直接更新相关条款，删除被替代的候选；讨论中的建议不得记为已确认决策。

设计宪章统一产品边界，implementation 冻结具体技术行为；发现冲突必须同步解决，不能单靠修改代码或测试视为完成决策。

维护发生在协作对话中，不依赖后台自动监听。继续讨论时先依据当前文档；遇到矛盾明确记录并解决，不静默覆盖。

## 2. 当前定位

主要创作参照是用户偏好的日系视觉小说。带历史记录的反复询问和循环选择是低频需求；它们需要支持，但不应作为主导系统复杂度的典型场景。不能仅根据这一风格偏好推定存读档、回滚、已读跳过等功能已被要求。

Ktory 是面向对白驱动游戏的叙事创作与接入系统。推荐工作流尽可能由 `.ktr` 统一组织文本、对白顺序、选择、分支、声明性的时间／同步关系和有剧情意义的演出交接；共享呈现设置减少逐句重复声明。具体演出由宿主引擎或演出工具制作，真实事件由游戏判定并报告，编辑器配置落实资源、对象及事件与脚本声明的绑定。跨文件共享、通用资源绑定与事件信号交接仍为产品目标，语法、接口或交付阶段另定；当前 Main／辅助与时钟修订见 D22；主副语言见 D20；具体行为见实现规格。

默认以 `.ktr` 为文本与剧情流程的唯一定义源。Timeline 可以暂时掌管播放时机，不必接管后续对白与分支的组织，也不应维护重复剧情流程。宿主直接调用分立段落是允许的另一种接入方式，不是常规创作的必需形式。具体引擎、表现形式和是否采用 Timeline 均不是定位前提。

“唯一置信源”按职责划分：Ktory 拥有剧情拓扑及会话执行状态，多轨目标包括各播放头的控制流与声明性的同步关系；游戏世界状态、资源与局部演出状态归宿主。仓库的核心源码仅在 `src/Ktory.Core` 维护，门户、桥接和生成包不能独立改写剧情语义。完整边界见宪章 §4 与工作流 §3。

Ktory 的产品目标是在结构化对白／动作拍、参数修饰符及同文件多语言的基础上，统一默认呈现、资源绑定与演出交接，减少重复配置和逐场景专用代码。独立运行时是否必要仍由具体语义与维护成本判断。Ink 同样具备宿主推进、选择、标签、外部函数及 Unity 接入；不以“只有 Ktory 能接演出”作为定位，也不以符号差异作为设计目标。

## 3. 已确认的决策

### 第一阶段验收基线（已确认）

用户确认：独自编写含对白、选择和演出触发的脚本，在同一文件维护译文，脱离 Unity 试读分支，再将同一脚本用于 Unity，足以开始实际项目使用。Unity 首阶段只需对话框与立绘显示，不要求实现 Timeline 集成或演出推进限制。独立试读器至少提供语言选择。

这一基线收窄的是第一阶段交付，不撤销此前确定的长期演出协作目标。Scope 初步收束，后续工作应将该基线转为一致的语言和运行时契约，而非继续无边界增加首阶段功能。

## 4. 创作责任边界

### Main／辅助播放头（2026-10-22 已确认、实施中）

同一文件章节不区分主副，运行身份属于播放头。唯一 Main 接收玩家输入，可 track 创建辅助、stopTrack 点名停止、awaitTrack 等待已创建实例；辅助遇这些控制直接忽略。辅助选择整体跳过分支和标签，不消费一次性选项。多个实例可以执行同一节。

辅助输出后直接继续，直到 at 或其他 Core 控制流边界；wait／next／AUTO／打印／duration 都不阻挡它，不默认估算阅读。Main 结束会话停止辅助，不自动 join；需要等就显式 await。停止执行不强制清屏，末句先于结束通知。每个播放头只有一条当前语句，后句进入就撤下前句，与显示位置无关；空 : 同样结束前句显示。等待下一句 at 时尚未进入新句，前句可按自身寿命保留。

track 默认只创建并排入调度，不保证初始化完成；`#.track(source="Init").await` 显式等待本次实例结束，具名可用同样写法。awaitTrack 用于等待已启动的具名辅助。具名辅助同声明每会话只创建一次、结束后不重启；匿名每次有效执行新建。具名钟全局唯一声明位置，首次执行创建后复用，存活至会话结束；匿名局部、默认初始空、失默认即回收；reset 保持 ID。source 不透明，空串等同省略，宿主可接管否则内置；暂时无值继续等待，不猜值。真实媒体和显示归宿主。

旧 parallel/lane 显式迁移，不保留旧运行语义，且不能保证旧嵌套／循环 join 机械等价转换。外部文件须显式 URL，格式与加载协议由用户延期；本文件多轨可先落实。细节见 implementation §2.6–2.9／§3.4。

### 主／副语言输出（本轮已落实）

文件 `defaultLang` 决定未标注文本归属及回退；运行时 `RequestedLanguage` 与可选 `SecondaryLanguage` 表示输出配置，通过 `SetLanguageOutput` 或分别设置主／副语言更新。关闭副语言时保持现有单语言使用行为。开启后，对白、旁白、Speaker 显示名和 Choice 标签分别解析主／副结果，并分别报告请求语言与实际语言；稳定的说话人、选项身份不随语言配置变化。

输出保持结构化，不拼成双语字符串。renderer 自行决定副语言的可见性、排版、字号、位置及交互。副语言是呈现配置，不是剧情状态；开关或切换时刷新当前活动内容，不移动执行位置、不重置调用／循环、不改变选项消耗、不重放修饰符。

本次文档落实单列采纳的工程决定：预估阅读时间默认只使用主语言实际输出；副语言开关不改变固定或预估计时。宿主若需要其他阅读策略须显式配置，不能由副语言开关隐式触发。主语言切换沿用现行刷新规则。副语言只取精确译文而不回退；缺失字段为 null，与该字段主语言实际语言相同则省略，不同语言文字相同仍保留。禁止伪标语言的原则不变。详见 implementation §2.5.4。

### 共享呈现设置（文件内默认修饰符已实现，资源绑定待落实）

名字的多语言映射、默认对话框、默认声音或声音组和表情资源对应关系应可集中定义，逐句只写变化。名字声明与呈现设置允许关联，也允许分别维护；不把说话人提升为完整游戏角色数据库。当前 `@speaker` 已实现名字、别名及缩进声明的默认修饰符，按句进行同名整组覆盖。

表情规则为：当前句有定义则使用当前句；否则回退适用的全局默认；两者均无定义则不展示。上一句的局部表情不得残留。“不展示”需要明确输出并由呈现端落实，不能只让解析器不做任何事。该规则不自动适用于持续播放的音乐等其他资源。

本轮默认修饰符使用文件作用域，按同名整组覆盖；不增加取消语法。跨文件共享定义、资源存储和绑定，以及缺失或错误资源名的诊断方式仍待设计。默认声音配置目标不使配音系统成为首阶段要求。

### 调查交互的组织方式与优先级

- 对纯文本调查中的“问过某话题”等叙事记录，用户认为没有必要下放到游戏侧，同时认可这会增加 Ktory 的内部状态复杂度。记录形式、作用域和持久化方式未定，不据此确认完整通用变量系统。
- 此类情景及循环选择在用户创作中较少见。此前“当前阶段充分支持脚本组织调查”的要求保留，但不等于循环调查是首阶段的主要体验或最复杂状态系统的设计依据。

- 脚本组织调查、游戏组织调查两种方式都需要支持，适应不同游戏的交互模式。
- 当选项间的差异主要体现在文本与叙事分支上时，由脚本组织调查；当单个选项需要处理大量额外游戏逻辑时，可以由游戏组织调查并调用 Ktory 段落。这是选用倾向，不是禁止脚本调用游戏逻辑的硬性分界。
- 当前阶段要求充分支持脚本组织调查。这一优先级不等于要求首阶段完成游戏组织调查所涉及的全部复杂场景；后者具体阶段范围未定。

### 阶段范围：核心与引擎接入

2026-09-26 的工作条件：已有 Unity 工程与本地 Ktory 接入位于另一设备。当前设备重点验证核心与桥接，远端工程提供真实使用反馈。无需为继续核心工作同步全部游戏资源；通过固定源提交、生成包提交与最小复现保持对应。仓库通用接入工具与用户已有游戏工程是两个不同对象。

- 引擎配套工具属于必要的交付方向，但不作为第一阶段的主要开发重点。
- 第一阶段同步实现 Unity 接入工具，用于在真实编辑器中测试 Ktory 的表现，并以接入实践验证核心设计。
- 其他引擎的接入暂不考虑开发；核心不绑定特定引擎的原则保留，不据此提前建设多引擎适配。
- Unity 首阶段接入支持对话框和立绘显示即可满足用户使用；Timeline 集成与演出推进限制不作为首阶段验收要求。具体配置界面未定，不承诺完整可视化编辑器或全部预设策略。

### 阶段范围：独立试读

当前已采用本地 ASP.NET Core Reader 与 WASM Reader，共用 C# 核心与前端。2026-09-26 用户进一步明确要求 VS Code 高亮扩展及编辑器内试读，因此将已有 TextMate grammar 包装为扩展，并复用 WASM Reader；这不扩大为完整 IDE、语言服务器或游戏模拟器。语言热切换的具体语义以 implementation 为准。

- 第一阶段需要能够脱离 Unity 试读 Ktory 脚本，不以启动游戏编辑器为前提。
- 试读器支持语言选择并无副作用地刷新当前显示，遵守 implementation 的刷新与计时契约。
- 本次确认的是独立试读能力，不自动扩大为完整 IDE、演出预览器、热更新或完整编辑器插件功能。
- Reader 跳过无法解释的演出标签，不模拟未知外部来源。Reader 未指定 source 时使用 Ktory 内置钟，`music.position` 明确解析为当前 BGM 播放器以秒为单位的实际播放头位置；缺少可用 BGM 时无值，保留 at 等待。VS Code 内置试读当前不播放音频。未来显式信号依赖需另定越过或人工确认策略；跳过未知演出不能被解释为真实信号已经发生。
- 遇到无法求值的外部选项条件时，忽略该条件，全部展示选项，供作者选择试读；不隐藏受其控制的选项，也不模拟外部状态。“基础行为”的准确集合尚需定义；本决定不要求忽略可正常求值的基础条件，不代表自动执行所有分支。
- 独立试读不验证 Unity 中的实际演出、外部状态或推进限制；试读通过不等于这些外部行为已得到验证。

### 阶段范围：多语言与配音

- 多语言是刚需，纳入第一阶段必要能力，不能以单语言实现作为阶段目标的替代。
- Ktory 输出给表现层时需要标明实际输出语言。请求英文但回退中文时，语言标识为 `zh`；请求语言与实际文本语言不混同。字段与主／副语言规则见 implementation §2.5。
- 请求语言缺少某句译文时，回退文件默认语言；用户确认 `defaultLang = zh` 且缺少英文译文时直接显示中文，不以缺译提示替代正文。试读器的额外缺译提示不是已确认的首阶段要求。
- 文件级 `defaultLang` 用于主语言回退；未标注文本归属及请求／默认双缺译的处理按 implementation §2.5 执行。
- 配音支持暂不考虑，不作为第一阶段验收要求；这不取消已讨论的通用演出触发或音效接入方向。
- 第一阶段以同一 `.ktr` 文件内维护多语言变体为主要工作流。用户通常独自完成写作与翻译，这种方式足够满足当前使用需要。
- 暂不提供译文提取、回填、独立翻译表或翻译协作工具。允许使用者自行维护多个语言版本的 `.ktr` 文档，但不据此承诺版本之间的自动同步、对齐或一致性维护。
- 本地化覆盖正文、名字和选项；不从“多语言刚需”推导完整本地化生产管线。

### 阶段范围：进度持久化与恢复

- 第一阶段可以不提供存读档能力，也不要求 Ktory 持久保存文件内播放进度。
- 文件级进度可由游戏记录最后一个完成播放的 `.ktr` 文件，作为阶段性方案；不要求 Ktory 自行维护跨会话播放进程。
- 最终目标是支持逐句恢复，具体阶段、接口和恢复范围尚未确定。画面、演出、音频时间点的恢复精度，以及全量回滚，不因这一目标自动纳入。
- 这里的“不记录播放进程”指无需持久化和恢复文件内进度，不取消正常播放所需的当前执行位置或会话内叙事记录。
- 文件完成记录能够表示粗粒度进度，但不能一般性地替代分支选择、背包等状态的保存；这些状态如何跨文件、跨会话处理留待后续定义，不以此要求首阶段增加存档系统。

### 已确认的方向

- 演出依赖可指完成，也可指中途节点。固定时间表达时间要求，信号表达事件要求；需要完成后继续时应引用完成信号，避免靠预估时长替代事件。
- 脚本声明剧情交接，游戏侧绑定并判定真实事件。文本播放策略继续按现行规格执行；`.wait(t)` 是最低停留且自身不自动推进，不是等待事件的新语法。两者的组合协议待设计。

- Ktory 承担对白创作与叙事编排，并能决定何时触发演出。
- 镜头、角色运动等具体演出可以在 Timeline 或其他宿主工具中制作。
- 剧本写出一个动作，不等于引擎已经具备识别、实现和验证该动作的能力。资源制作及其与脚本的关联是必须面对的工作。
- 音乐、音效可以放在脚本或演出工具中，依据场景需要选择；用户倾向于用脚本更直接地把握声音节奏。
- 镜头通常与场景和动画配合更紧密，用户优先考虑在演出工具中制作。这是创作偏好，不是禁止脚本触发镜头的规则。

### 用于检验边界的场景

艾莉丝说话时走向门口；走到一半，爆炸打断台词；镜头转向窗外；声音结束后，玩家选择继续追问或离开。

用户希望整段叙事都可以写进剧本，但不希望因此被迫用文本定义和测试所有坐标与运动细节。

“走到一半”如何由游戏侧可靠识别仍未定。按修订后的 D13–D15，脚本可显式依赖该节点，由游戏侧绑定并报告；具体通知与推进协议尚未确定。“一半”不能擅自解释为时间或路程的 50%。

### 已确认的情景：对白与移动同时进行

艾莉丝说“门外有人，我去看看”，同时开始约四秒的走向门口演出；下一句“奇怪，什么都没有”发生在到达之后。本情景的点击表示确认对白，暂不讨论打字机快显。

用户确认在该同步情景下以下默认行为及两种可选行为均需支持。一般文本门控仍不隐式等待所有演出。2026-09-26 修订允许脚本显式选择演出依赖；下表描述这一特定同步情景，不规定等待记录的承载模块，也不改变现行 `.wait` 期间点击丢弃规则。确认与信号如何组合、如何配置且避免逐场景样板代码仍待设计。

| 行为 | 玩家在移动完成前确认 | 移动先完成 |
| --- | --- | --- |
| 默认：各自确认、条件汇合 | 保留当前对白的确认；等移动完成后自动进入下一句，无需重复点击。 | 等玩家确认当前对白后继续。 |
| 可选：点击跳过当前演出 | 跳过剩余过程，直接从到门口之后的场景继续播放。 | 依当前段落的推进规则继续。 |
| 可选：演出完成前点击无效 | 提前点击不保留；演出完成后需要再次确认。 | 等玩家确认后继续。 |

若有多个需要确认的断点，各自确认。本次确认不构成对后续多个断点的一次性确认。默认等待不意味着暂停所有表现：待机和环境声音等可继续。

跳过当前演出的终点、场景状态如何落实，以及中途事件是否执行尚未确定。“跳过”不能未经讨论推广为跳过整个剧情、所有断点或玩家选择。

## 5. 尚未确定的范围与设计

### 已确认的创作痛点与验收方向

用户报告：在其 Ink 与 Timeline 整合实践中，需要放置大量 eventSignal，让解释器监听，并在对白期间暂停 Timeline，在脚本中手动指定暂停与继续。Ktory 应避免重复这一体验。这是用户实践的记录，不是对 Ink 所有集成方式的结论。

因此，“支持双向通信”只是能力要求，“常见配合无需逐处手写协调”是独立的作者体验要求。减少样板协调不能以限制原有叙事表达目标为代价。

候选验收场景（待确认）：外部演出到达对白段落后，玩家阅读或选择，结束后演出继续；作者不必分别维护事件标记、监听逻辑及成对的暂停与恢复命令。对应工具和运行时如何实现尚未决定。

需要区分具有叙事意义的特殊同步节点与纯粹用于连接两个播放器的重复操作。文本播放完成开启文本门控已确认；哪些演出应继续、哪些需要额外等待，以及交互确认与演出完成的组合仍待设计。不能直接假定“每句对白暂停整条 Timeline”。

### 演出结束边界：问题与候选方案

用户指出：脚本只记录演出触发，不记录结束点；如果要求演出端正确结束，结束边界从哪里来？不能将逐段标记所有起止点的负担隐藏在“演出端负责”中。

脚本可显式声明节点或完成信号依赖，游戏侧判定真实事件；如何绑定资源边界与片段节点、如何匹配本次播放、由哪个模块保存依赖记录仍待工程设计。

自然播放完成、点击快显文本、跳过演出并落实结果是不同能力。外部接入层能否正确完成跳过及其中状态修改，需要单独约定，不能仅靠“有结束时间”推导。

### 后续剧情能力（已确认需求，延期）

| 能力 | 作者体验 | 仍待确定 |
| --- | --- | --- |
| 按当前情况选择剧情 | 玩家发起交谈等交互时，按游戏状态与叙事记录选择合适段落，减少游戏代码中的剧情枚举 | 触发入口、选择优先级、冲突处理与记录归属 |
| 交还玩家操作后继续剧情 | 剧本暂时交出操作，约定的游戏事件发生后继续原来的剧情流程 | 恢复与取消、跨场景、存档与生命周期范围 |

两项均不进入当前冻结 API 或第一阶段验收，也不等于完整任务系统或通用游戏状态机。“状态打通”旨在减少同一事实的重复保存和手工同步，不代表全部状态迁入 Ktory；具体记录分别定义所有者。

### 后续讨论顺序（工程建议）

1. 先落实本轮文档边界，保留当前执行契约与首阶段验收范围；继续核心正确性和回归工作。
2. 新能力先细化默认呈现的引用、作用域与输出，再以现有剧本验证减少重复配置的收益。
3. 随后设计编辑器绑定和信号交接；建议先验证“播放一个演出，完成后继续”，再覆盖中途节点、取消、失败、跳过与过期通知。
4. 为独立试读定义显式交接的越过或人工确认方式，标明其不是真实演出验证，不建设完整游戏模拟器。
5. 两项后续剧情能力继续延期；触发、冲突、跨场景和存档范围另行讨论。

以上是依赖顺序建议，不是新的工期或阶段承诺。局部取消默认值、错误资源处理、信号 API 与新 AST 都保持待决；完整工程问题见 [engineering](ktory-engineering_v1.md)，配置／载荷／推进的影响清单见 implementation §1.4。
