## 1. 总体判断

**v1 的主要功能路径已经成形，当前处于契约收口、跨端一致性与真实项目验收阶段；尚不能宣布 v1 完成。**

已有路径是：编写同文件多语言 `.ktr` → 解析与按拍执行 → 独立 Reader／VS Code 试读 → Unity 导入、宿主接入与会话调试。Core、呈现时序、WASM 桥接和 VS Code 已有实际运行的自动化证据。尚欠缺的是已确认契约的若干实现修正、发布门禁，以及绑定固定版本的 Unity 首阶段验收记录。

| 评估维度 | 当前判断 | 对完成度的含义 |
| --- | --- | --- |
| 首阶段功能主干 | 大部分已实施 | 不是从零构建解释器或试读器的阶段；可以用真实脚本继续接入与反馈 |
| 已确认契约一致性 | 部分完成，存在可复现差异 | 测试全绿仍不足以认定 v1 完成；已有测试也可能固化旧兼容行为 |
| 本机验证 | Core、Reader 时序、VS Code 真 Webview 已通过 | 证据较完整地覆盖了本机主要路径，但未覆盖全部异常组合与宿主生命周期 |
| Unity 使用闭环 | 接入代码与调试工具已实施，实机证据待补 | 用户另一设备已有接入；本次无法判定其固定版本上的对白、选择、立绘与输入是否全部通过 |
| 分发与发布 | 生成流程存在，门禁及版本追溯未闭合 | 本地通过不保证 Reader／UPM 发布的是同一已验证提交 |
| 新定位中的产品能力 | 目标已确认，主体待实现 | 默认呈现、配置绑定、显式信号交接不能算作现有成果，也不追加为 v1 完成门槛 |

当前适合以预览版本继续真实项目验证。距离首阶段验收最近的工作是收敛上述缺口，而非增加存档、完整演出系统或更多编辑器功能。完成度以这些验收项逐项关闭衡量，测试数量不是完成百分比。

## 4. v1 未完成项与已确认差异

下表前三列来自实际复现或明确源码路径。修复应先形成有区分能力的回归，再改实现，并同步受影响样例；不能仅为保持旧测试全绿而改写规范。

| 编号／性质 | 最小输入或操作 | 当前实际结果 | 收口要求与验证方法 |
| --- | --- | --- | --- |
| V1-01 已确认契约偏差：默认入口 | 脚本 `=== Side ===\n  : named body`，不传入口调用 `Start()` | 输出 `named body` | implementation §2.4 规定命名节仅显式进入；默认根节不应自动执行它。分别断言无入口与显式 `Side` 的不同轨迹，检查 Reader 的默认入口是否一致 |
| V1-02 已确认契约偏差：节归属 | 解析 `=== Side ===\n: unindented body` | `Side.Steps.Count == 1`，根节为 0 | 顶格文本按规格应恢复根节，不能被兼容分支吞入命名节。验证空命名节、缩进正文、退回根节、调用返回，并检查旧样例迁移 |
| V1-03 明确实现缺口：未知容器 | `#mystery\n  + [A]\n    : branch`，订阅 trace 后启动 | 能展示 choice；只有 `Node:#mystery`，没有警告 | §2.2.3 要求包含容器名与位置的 Warning。当前尚无可见 Handler 注册／查找实现，所有容器进入基础 choice 路径；需按规格明确 SDK 分工并补齐降级诊断，覆盖可选和零可选场景 |
| V1-04 诊断缺口：悬空修饰符 | 解析 `.effect\n: first` | 解析成功，正文保留，但标签计数为 0，`.effect` 消失 | 违反“无静默丢弃”和最近上方锚点规则的可诊断要求。为缺少锚点给出定位诊断；最终诊断类别按实现契约补齐，不擅自挂到下一句 |
| V1-05 桥接一致性缺口：失败重载 | `RunnerSessionService.Start(旧脚本)` → `Start("-> Missing")` 抛错 → `Step()` | 仍输出旧脚本第二句 `old second` | HTTP 不应在重载失败后意外继续旧剧情。WASM 已有 [对应回归](../tests/Ktory.Core.Tests/PreviewBridgeTests.cs) 并通过；为 HTTP 添加相同语义的失败、拒绝继续、修复重载用例，再核对前端表现 |
| V1-06 C05 尚未完整落实：跨会话输入 | 同一 Sequencer 第一次 `Start()` 取得 ID 1；再次 `Start()`；调用 `Step(旧 ID 1)` | 新会话 ID 也是 1，旧输入推进到 `second` | 单个 presentation ID 只能提供部分保护。需明确会话世代／呈现标识的所有权和拒绝契约，验证重启、替换、关闭后旧点击／选择／计时回调无效。Reader epoch、VS Code revision 已有局部保护，不能推导所有宿主安全 |
| V1-07 发布门禁缺口 | 检查三条 workflow | VSIX workflow 跑 Core 与扩展单测；Reader／UPM 可独立直接发布 | Reader、UPM 必须依赖同一源提交的相关测试成功；Reader 25 项与 Webview 集成尚未进入现有 CI。验证测试故意失败时不能发布，并补齐测试／公共构建配置等相关触发路径 |

V1-01 的旧行为甚至已有 `Sequencer_DefaultStart_WhenNoRootSection_StartsAtFirstNamedSection` 测试保护。因此，“97 项全绿”与“已确认规格全部符合”是两个结论。V1-06 属于原则已确认、完整技术协议待定的缺口，不预先指定必须使用哪种 token 或把等待状态放在哪层。

上述六个运行探针可在引用 Core 和 Runner 的临时 .NET 控制台中复现；脚本中的 `\n` 表示真实换行。V1-05 的旧脚本为 `: old first\n: old second`，入口传 `null`、语言传 `zh`；V1-06 为 `: first\n: second`。探针直接调用公共方法，HTTP 项验证的是服务层，并未声称执行了真实 HTTP 网络往返。正式修复时应将这些用例纳入仓库测试。

另有边界需明确并验证，尚未在本次判为已确认 bug：请求语言与默认语言都缺失时，正文／名字／选项如何一致处理；宽容试读求值与游戏严格策略如何显式配置；全体错误和 Warning 如何统一携带位置并透传至各宿主。应围绕具体作者场景收敛，不扩张为完整表达式语言或格式化器项目。

## 6. 下一阶段计划建议

以下是实施顺序建议，尚未自动开工或新增 v1 范围。既有游戏接入可以同时提供反馈，不必等待本机所有工作结束才开始实机验证。

### 第一优先级：完成 v1 收口

1. **修复会改变剧情或接收旧输入的边界**：先 V1-05、V1-01／02，再明确 V1-06 的会话拒绝契约；同步受影响桥接、示例和旧回归。
2. **补诊断与可追溯门禁**：落实 V1-03／04，以及同提交验证后才发布；让 Reader 时序和关键集成测试进入对应检查链，避免已有回归只留在本机。
3. **用固定版本完成一次真实 Unity 闭环**：生成 S/P，交给另一设备已有工程；复验对白、选择、立绘、语言、重启与时序。可脱离 UI 的问题转成本机回归，通用修复回主线，游戏专用逻辑留在游戏。

v1 完成判断应至少包含：已知的入口／节归属／静默丢弃／失败重载问题关闭；未知容器按规格降级并诊断；宿主会话推进与旧输入规则明确且有证据；独立试读与 Unity 首阶段场景在可追溯版本上通过；发布路径不能绕过相关验证。无需等存档、配音或信号系统完成。

### 接着：做一项可测量的产品改进——默认呈现

以一小段真实灯塔对白为材料，先设计共享名字／呈现设置、局部覆盖及表情清除的最小闭环。关键验收是：

- 连续多句共用默认设置，脚本只书写变化；插入或移动一句不会意外继承上一句局部表情。
- 本句表情 → 适用默认 → 不展示；无可用表情时输出并执行清除，Reader 与 Unity 都能解释该结果。
- 配置一个新角色／替换资源后，复用既有接入；用真实项目记录逐句重复声明、配置步骤与所需新增代码。

先明确引用方式、作用域、缺失资源和局部取消默认的语义，再改 AST／API。名字、默认对话框、声音或声音组和表情映射属于整体目标；首个增量可以先验证默认表情与对白呈现，不把配置声音扩大成完整配音系统。

### 再接着：可配置绑定与一次完成信号

选一个具体能力，例如“触发移动演出，完成后继续剧情”。形成 `.ktr` 声明、编辑器绑定、真实完成通知和下一拍之间的一条完整路径；随后用第二个同类场景复验复用性。

验收重点：新增第二段同类演出主要改内容与配置；不反复增加监听／暂停／恢复／清理代码；重复、迟到、取消、跨会话的通知不会误推进；人工确认与演出完成的两种先后顺序按已确认场景收敛。新增能力可以需要一次宿主代码实现，不能承诺所有行为零代码。

等待记录承载层、通知标识、取消与清理、试读越过／人工确认策略仍需设计。先证明“完成后继续”的可靠性，再扩展中途节点、无对白段落和复杂交接；不冻结 `.await` 或恢复历史统一五阶段生命周期。

### 后续延期项

按当前世界／历史情况选择剧情、交还玩家操作后恢复原剧情，两项需求保留但延期。逐句存读档、配音管线、翻译提取回填、Timeline 深度集成、其他引擎和完整 IDE 也不抢占当前收口工作。现有调用、循环与消费记录不等于这些产品能力已经完成。

## 7. 此刻的工作重心

当前设备应围绕“已确认的语义在同一版本、不同宿主中可重复成立”组织工作：把已复现的差异关掉，补能发现它们的测试，建立发布门禁；另一设备提供同一包版本的真实 UI、资源与生命周期反馈。
